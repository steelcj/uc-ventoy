# Session record, 2026-11-15

This is a record of the session, not current documentation. Where it and the documents disagree, the documents win.

The session worked from [the kickoff note](2026-11-15--20-16-45-kickoff-make-uc-ventoy-fulfil-raw-node-contract.md). Nothing was committed, and nothing was installed on a node. Every statement below about an installed system comes from templates, package contents and offline tests, and is marked as such in [contracts.md](../contracts.md).

## Outputs

- [`shared/foomuuri/00-raw-node.conf.j2`](../../../shared/foomuuri/00-raw-node.conf.j2): the raw node firewall, rendered once and embedded identically in every target. `shared/nftables/nftables.conf` is removed.
- [`shared/systemd/foomuuri-raw-node.conf`](../../../shared/systemd/foomuuri-raw-node.conf): a drop-in for `foomuuri.service`, written on the Ubuntu targets only.

- [`shared/systemd/raw-node-firstboot.service`](../../../shared/systemd/raw-node-firstboot.service): also ordered after `cloud-init-network.service`, the name of cloud-init's network stage on Ubuntu 26.04.
- `bin/build`: `BASELINE_VERSION` 0.3.0, `CONTRACT_VERSION` 0.1.0, the optional inputs `ssh_port` and `ssh_sources`, the Foomuuri render and check, `--check-firewall-only`, a self-test of the report, and a check that every target writes the required files. The `nft` check of `nftables.conf` is gone.
- The three templates: `foomuuri` package, port drop-in, firewall file, `nftables.service` masked, `ufw.service` masked on Ubuntu, `foomuuri.service` enabled.
- Documents: new [contracts.md](../contracts.md), updated baseline, target documents, README and example confirmation.

## Decisions

- The earlier draft in `uc-ventoy-foomuuri.tar.gz` was used as a starting point. Kept: the firewall file, input validation, the port drop-in and `--check-firewall-only`. Changed: the points under Findings. Not taken over: the extra `RAW_NODE_FIREWALL`, `RAW_NODE_SSH_PORT` and `RAW_NODE_SSH_SOURCES` variables, because the report measures those values instead of reading them.
- `foomuuri-boot.service` is not enabled anywhere. It is a static unit that `foomuuri.service` starts by itself. `systemctl enable` on it does nothing on 0.27 and 0.31 and fails on 0.22, where a failing `late-commands` entry would fail the installation.
- The drop-in for `foomuuri.service` goes on the Ubuntu targets only. Debian has no cloud-init and keeps the packaged unit. Confirmed later in the session: the drop-in is acceptable because it provides what the contract asks for, it stays a uc-ventoy matter rather than a contract one, and it is explained in [raw-node-baseline.md](../raw-node-baseline.md#the-foomuuri-drop-in-on-ubuntu).
- The report follows the contract's format exactly, including plain MAC addresses, although some of them change type when parsed. That is recorded for uc-contracts rather than worked around.
- `--check-firewall-only` fails without root or without Foomuuri, because a check that did not run is not a pass. A normal build only warns.
- The baseline document keeps the number 0.3.0, the value the kickoff set for `BASELINE_VERSION`. Its change log explains that the entry of the day before used the same number for the nftables firewall, which `bin/build` recorded as 0.2.0.

## Findings

### Foomuuri versions and the firewall file

Package versions, from the archives: 0.27-2+deb13u1 on Debian 13, 0.22-1 on Ubuntu 24.04, 0.31-1 on Ubuntu 26.04, the last two in `universe`.

The three packages were unpacked and run in an unprivileged user and network namespace, where `nft` works without root.

- The rendered file passes `foomuuri check`, including the `nft` check, on all three, for port 22 from anywhere and for another port with mixed IPv4 and IPv6 sources.
- The catch-all interface `*` fails on all three.
- `foomuuri start` creates only `table inet foomuuri` and `foomuuri stop` removes only that table. No version uses `flush ruleset`.
- The 0.27 and 0.31 rulesets are identical. 0.22 differs in details that do not change what is accepted, except that the later versions also accept IGMP queries to 224.0.0.1.
- Without root, 0.22 fails in `nft` with a permission error, while 0.27 and 0.31 skip `nft` and still print `check success`. The draft would have reported a pass in that case. `bin/build` now treats any run without root as unchecked.

### Unit ordering (RN-FW-04)

- `foomuuri.service` in all three versions: `After=local-fs.target`, `Before=network-pre.target`, `Wants=network-pre.target`, with systemd's default dependencies left on. 0.27 and 0.31 add `Wants=` and `After=foomuuri-boot.service`.
- `foomuuri-boot.service` in 0.27 and 0.31: no install section, and `ConditionPathExists=/var/lib/foomuuri/good.fw`. It is skipped at first boot, so `foomuuri.service` is what puts the firewall in force then.
- Ubuntu 24.04: cloud-init's `cloud-init.service` has `After=systemd-networkd-wait-online.service` and `Before=sysinit.target`. With the default dependencies of `foomuuri.service` this is a cycle. `systemd-analyze verify` on a root built from the packaged unit files of systemd, cloud-init, Foomuuri and OpenSSH reported it and deleted the `cloud-init.service` start job. With the drop-in there is no cycle. The nftables design did not have this problem, because `nftables.service` has no default dependencies.
- Ubuntu 26.04: `cloud-init-network.service` is no longer ordered after wait-online, and the same check finds no cycle. cloud-init starts wait-online itself when it decides it needs the network, which would block a Foomuuri that waits for `sysinit.target`. The drop-in is written there as well.
- Debian 13: no cloud-init, `networking.service` is ordered after `network-pre.target`, and the check finds no cycle.

The check used the `systemd-analyze` of this workstation, systemd 255, which is the Ubuntu 24.04 version. It ignored a few directives that only newer systemd knows when reading the 26.04 and Debian 13 unit files. None of them concern ordering.

### SSH port on Ubuntu (RN-SSH-01)

Both Ubuntu releases install `sshd-socket-generator`. The packaged binaries from 24.04 and 26.04 were run against a default `sshd_config` plus a drop-in with `Port 2222`. Both wrote `ssh.socket.d/addresses.conf` with listeners on 2222. With `Port 22` the generator writes nothing and the socket's default applies. No socket override is needed.

`sshd -T` fails as root while `/run/sshd` does not exist, which is the case on Ubuntu until the first connection starts sshd. `sshd -G` prints the same configuration without that directory. This was tested with the sshd binaries of all three targets. The report uses `-G` and falls back to `-T`.

### Accounts on Ubuntu

- Current Subiquity creates the `identity` user during installation and passes cloud-init only the name, the SSH keys and `ssh_pwauth`. cloud-init installs `authorized_keys` at first boot, in its network stage. Subiquity also writes `/etc/hostname` and sets `preserve_hostname`, so `99-raw-node.cfg` repeats what the installer already does.
- cloud-init's `set_passwords` writes `50-cloud-init.conf` with `PasswordAuthentication yes` when `allow-pw` is true. `10-local-auth.conf` sorts first either way.
- No `sudo` rule is passed to cloud-init, so sudo comes from the `sudo` group and asks for the password.
- Ubuntu 26.04 uses sudo-rs. Its binary contains the same sentence the report looks for in the `sudo -l` output.

### Confirmation format

- PyYAML reads `mac: 52:54:00:12:34:56` as the integer 41135085296, because YAML 1.1 has base 60 integers. Any MAC whose parts are all decimal and below 60 is affected, which includes part of the QEMU range.
- A `machine_id` made of digits only is read as an integer.
- `0.1.0`, `0.3.0`, the timestamp and the IPv6 flow lists parse as intended.

### Debian installer

The `late_command` is 18.8 kB after joining, about twice the earlier size. The installer's `debconf-set-selections` script and the cdebconf sources show no fixed limit: buffers grow as needed. The script drops every line that begins with `#` before joining continuation lines, which does not touch embedded files, because their lines begin with spaces and a quote.

## Tests run

- `bin/build` with the real input: three targets, self-tests OK, shellcheck clean.
- `bin/build --check-firewall-only` as root inside a user namespace, with each of the three Foomuuri versions, default and custom inputs: OK. As a normal user: fails with the instruction to use sudo.
- Input validation: bad ports, a string instead of a list, host bits, a hostname as source, unknown keys.
- The embedded files were extracted from each rendered answer file the way the installers do it. The firewall file, both SSH drop-ins, both scripts and the first-boot unit are byte for byte the same on all three targets.
- `raw-node-report` against a made-up `/sys` tree and stub commands: wired, wireless with a randomised address, a bridge, a WWAN device, no interfaces, a missing user, and both sshd fallbacks.
- `systemd-analyze verify` on offline roots for all three targets with the shipped unit files.

## Not done here

- No installation. Every "needs an install to confirm" in [contracts.md](../contracts.md) is open, and so is the retest of Debian 13 on metal.
- `sudo bin/build --check-firewall-only` was not run with real root: the session had no sudo, and Foomuuri is not installed on the workstation. Installing it was left as a decision, because it adds a dependency.
- ShellCheck is not installed on the workstation either. A copy of ShellCheck 0.10.0 in a temporary directory was used.

Everything was downloaded to a temporary directory and nothing was installed: the Foomuuri, cloud-init, OpenSSH, systemd, nftables, ufw and sudo-rs packages of the three targets, a ShellCheck binary, and a few source files of Subiquity, cdebconf and the Debian preseed package.
