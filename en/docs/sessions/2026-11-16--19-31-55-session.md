# Session record, 2026-11-16

This is a record of the session, not current documentation. Where it and the documents disagree, the documents win.

The session started from an error in `bin/build --stick /media/initial/Ventoy --dry-run`. Nothing was committed, and nothing was installed on a node.

**The first write to the stick did not happen.** It was reported as done and verified. That report was wrong, and the reason is under [The stick was offline](#the-stick-was-offline). The stick was written at 19:47, after the build had been changed, and that write was verified after a remount: see [The second write](#the-second-write).

## Outputs

- [`bin/build`](../../../bin/build), in `install_on_stick`:
  - The stick is accepted when it has `ventoy/` or `iso/`. Before, a missing `ventoy/` was an error. The error is now `neither ventoy/ nor iso/ found; is this the Ventoy data partition?`.
  - `ventoy/` is created when it is missing.
  - The output says `would create` or `creating` for `ventoy/ventoy.json` when there is no such file yet, and `would update` or `updating` when there is one.
- [`bin/build`](../../../bin/build), added after the failed write described below:
  - `check_stick_online` reads the state of the disk behind the stick from `/sys` and refuses anything other than `running` (SCSI and USB) or `live` (NVMe). It runs before the ISO listing, in a dry run as well, and again after the write. A file system with no such state, for example a folder on tmpfs, is not checked.
  - `write_through` replaces the plain copies. It writes, calls `fsync` on the file and on its folder, drops the cached pages, reads the file back and compares. The backup of `ventoy.json` goes the same way.
  - An error from any of these ends the build with `writing failed: ... The stick is NOT complete.` and exit 1. A good write ends with `written to the device and read back: OK`.
- [`README.md`](../../../README.md): in the dry run example, the error line was replaced with the output of the fixed build. The new `read back: OK` line was added to the example of a real write. The paragraph below it, "Dry run output notes", still mentions a second `ventoy.json`, which that output does not show. It was left as it is.

## Decisions

- Ventoy does not create a `ventoy/` folder on the data partition. The user adds it together with `ventoy.json`. A freshly prepared stick therefore has none, and the old check rejected it.
- `iso/` was chosen as the second sign of the data partition, because the layout of this project puts every ISO under `/iso/<distro>/<version>/`. A path with neither folder is still refused, which catches a mistyped `--stick`.

## Findings

### The stick was offline

The stick is a SanDisk Cruzer Fit, 29.3 GiB, on USB port 3-1, seen as `sdb`: `sdb1` is the exFAT data partition labelled `Ventoy`, `sdb2` is `VTOYEFI`.

From the kernel log of the workstation, local time:

| Time | Event |
| --- | --- |
| 11:33:33, 11:35:36 | Two kernel stack traces that include `exfat_kill_sb`. Not examined further. |
| 11:35:51 | `USB disconnect` while writes to `sdb` were outstanding. |
| 11:35:54 | The stick is attached again. On mounting: `exFAT-fs (sdb1): Volume was not properly unmounted. Some data may be corrupt. Please run fsck.` |
| 11:54:21 to 11:55:20 | Five USB resets, then `Device offlined - not ready after error recovery`. A write had been waiting for 88 seconds. |
| 11:55:20 onwards | `rejecting I/O to offline device`. 154 error lines for `sdb` in that hour. |
| after 11:55:20 | No USB or SCSI event for the stick for the rest of the day. |
| 19:29:58 | Write errors again, `lost async page write` on `sdb1`. This is the write of this session. |
| 19:31 | `/sys/block/sdb/device/state` reads `offline`. |

What follows from this:

- The partition stayed mounted, and the kernel kept answering from memory. The listing of `/media/initial/Ventoy` at the start of the session, with `iso/` and three ISOs, came from memory, not from the stick.
- `bin/build --stick /media/initial/Ventoy` exited with 0 at about 19:29. The three answer files and `ventoy/ventoy.json` went into memory only. None of them is on the stick.
- The check after the write compared the files with `cmp` and printed `ventoy.json`. Both read back from memory, so both passed. `sync` returned without an error. A `find` over the stick in the same command printed nothing, which was a sign of the problem and was not followed up.
- A minute later the root of the mount listed as empty, and `ventoy/` gave `Input/output error`.
- Probable, not checked: the ISOs on the stick are incomplete. `iso/` was last changed at 11:37, and writes were failing from 11:54, so a copy was probably running when the stick went offline. The stick cannot be read in its present state.
- The stick failed twice in twenty minutes on the same port, once as a disconnect and once after resets. The stick, the port or the contact between them is unreliable. Which one is not known.

### What bin/build did not notice

At the time of the failed write, `install_on_stick` copied the files and wrote `ventoy.json`, and reported success when those calls returned. On a device that has gone offline they return without an error. The build did not flush the files to the device or check the result, so it could not tell this case from a good write. The user asked for this to be changed, and it was: see Outputs.

### The stick after it was plugged in again

The user plugged the stick in again at 19:33 and 19:36, now on USB port 3-7. Its state is `running`. On both mounts the kernel logged `Volume was not properly unmounted. Some data may be corrupt. Please run fsck.` The file system has not been checked.

Sizes of the ISOs on the stick against the copies under `~/iso`:

| ISO | On the stick | Under `~/iso` |
| --- | --- | --- |
| `windows/Win11_25H2_English_x64_v2.iso` | 4 623 773 696 | 8 471 603 200 |
| `ubuntu/24.04/ubuntu-24.04.5-live-server-amd64.iso` | 2 902 433 792 | 4 080 486 400 |
| `ubuntu/26.04/ubuntu-26.04.1-live-server-amd64.iso` | 2 927 861 760 | 2 927 861 760 |
| `debian/13/debian-13.7.0-amd64-netinst.iso` | 792 723 456 | 792 723 456 |

The Windows ISO on the stick is cut short. It was being copied when the stick went offline. The two Ubuntu 24.04 files differ in size, and which of them is the right one is for the checksums to say.

### Read errors, and a busy volume

To get those checksums, `bin/check-isos /media/initial/Ventoy/iso` was started in the background at about 19:38. Two things came of it:

- Between 19:40:13 and 19:41:31 the kernel logged 148 lines of `critical medium error` with `Unrecovered read error` for `sdb`, in sectors 7 081 280 to 7 271 232. The stick could not read that area. Whether the cause is the interrupted writes of the morning or a worn stick is not known. Which file lies there was not determined.
- The user tried to unmount the stick and got "Volume is busy". The only process holding the volume was this check, which had `ubuntu-24.04.5-live-server-amd64.iso` open. No `bin/build` process was running, so the build was not hanging. The check was stopped at 19:43:49 after five minutes, before it had printed a result, and the stick was unmounted and ejected a second later.

The user reported the busy volume as an issue on GitHub, as a build that hangs after failing. The cause found here is different.

### The file system check and the Ubuntu 24.04 ISO

- The user plugged the stick in again at 19:45. It was mounted at 19:45:01, and `sudo fsck.exfat /dev/sdb1` (exfatprogs 1.2.2) ran at 19:45:08, on the mounted volume. Result: `clean. directories 8, files 11`. The check reads the structure of the file system, not the contents of the files, so it says nothing about the read errors or the ISOs.
- The `SHA256SUMS` files for Ubuntu 24.04 on the stick and under `~/iso` are identical. The copy under `~/iso`, 4 080 486 400 bytes, matches its checksum. The copy on the stick has the same name and 2 902 433 792 bytes, so it is cut short as well.

### The second write

`bin/build --stick /media/initial/Ventoy` at 19:47:08: exit 0, `creating ventoy/ventoy.json`, `written to the device and read back: OK`. The device stayed `running`, and the kernel logged nothing for it during the write.

The stick was then unmounted and mounted again with `udisksctl`, which empties the cache. Read fresh from the device, the three answer files and `ventoy/ventoy.json` are byte for byte the same as those in `build/`.

On that mount the kernel again logged `Volume was not properly unmounted`. The flag that causes the message is still set on the stick. The check at 19:45:08 ran on the mounted volume and did not clear it.

## Tests run

- `bin/build --stick /media/initial/Ventoy --dry-run`: exit 0, with the `Stick:` section and `would create ventoy/ventoy.json`. The logic is correct, but the listing it worked from came from memory, as described above.
- `bin/build --stick` on a temporary folder with only `iso/` in it, on the local disk: the answer files and `ventoy/ventoy.json` were created. A second run reported `updating` and made a backup of `ventoy.json`.
- `bin/build --stick --dry-run` on an empty temporary folder: refused with the new error, exit 1.

All three ran with the real input and the Python of the virtual environment. The self-tests of the three targets passed in each run.

After the flush and check were added:

- The three tests above again, with the same results. A good write now ends with `written to the device and read back: OK`.
- A `--stick` path that does not exist: refused with `cannot be read`, exit 1.
- `stick_device_state` on the real devices: `('sdb', 'running')` for the stick, `('nvme0n1', 'live')` for the internal disk.
- Three failures, simulated by loading `bin/build` in a small driver script and replacing one function each time: `fsync` raising an I/O error, the device state reading `offline`, and a read back that differs. Each ended with a clear error and exit 1. With the state `offline` the build stopped before the ISO listing, in a dry run as well.
- `bin/build --stick /media/initial/Ventoy --dry-run` on the stick after it was plugged in again: exit 0, `would create ventoy/ventoy.json`.

Not tested: the new code against a device that really is offline. The stick had been plugged in again by the time the code was written.

## Not done here

- The answer files and `ventoy.json` are on the stick, but the stick is not ready to install from:
  1. The Windows 11 25H2 and Ubuntu 24.04 ISOs on it are cut short and have to be copied again.
  2. After copying, run `bin/check-isos` on the stick and look at `journalctl -k` for read errors. If they come back, the stick should be replaced.
  3. The file system check was not repeated on the unmounted volume, so the "not properly unmounted" flag is still set.
- `sudo bin/build --check-firewall-only` was not run. The build again reported the firewall as "not checked by nftables".
- No installation from the stick.
- The "Dry run output notes" in the README were not brought in line with the new output.
